Tema 1

El mapa del sistema

PetCore es un sistema de gestión para una clínica veterinaria. Tiene cuatro piezas que comparten los mismos datos: una API, un portal web para el personal, una app móvil para los dueños de mascotas y una base de datos Oracle.

PiezaTecnologíaQuién la usa
APISpring Boot (Java 17), 51 módulos, desplegada en un dyno Eco de HerokuTodo lo demás
Portal webJavaScript con módulos ES, Bootstrap y SweetAlert2Administrador, Veterinario, Recepcionista y Farmacéutico
App híbridaCapacitor (Android e iOS) con HTML y JavaScriptPropietarios de mascotas
Base de datosOracle: 51 tablas y 17 triggersGuarda los datos y hace cumplir reglas (stock, capacidad, turnos, IVA)

Dos canales entre el cliente y la API

REST (pedir y guardar)

El cliente pregunta con fetch y la API responde con JSON. Es la vía para leer, crear, editar y borrar.

WebSocket (avisar)

La API empuja un aviso corto cuando algo cambia. La pantalla vuelve a pedir los datos por REST.

Para recordar. El sistema es un solo proceso, sin balanceador. Muchas decisiones (códigos en memoria, sesiones de WebSocket en memoria, pools pequeños) salen de ese hecho.
Tema 2

Cómo viaja un dato entre el frontend y la API

Ninguna pantalla llama a la API directamente. Cada módulo tiene un archivo de servicio (services/*_service.js) que arma la URL, el método y el cuerpo. Por debajo, un fetch parcheado se ocupa de lo repetitivo.

El recorrido completo

→

→
Spring SecurityCORS, JWT, rol
→
Controllervalida el DTO
→
Servicereglas y transacción
→
Repositoryconsulta a Oracle

Las capas de cada módulo

CapaPara qué sirve
ControllerDefine la URL y el método. Recibe el JSON y lo valida con @Valid.
DTOLo que viaja por la red, con sus reglas (@NotNull, @Size, @Pattern).
ServiceReglas de negocio y transacciones. Convierte entre entidad y DTO.
RepositoryConsultas JPA y JPQL a Oracle.

Cómo se envían las solicitudes

Qué se haceCómo
LeerGET con la ruta y los parámetros (?texto=&page=&size=)

EditarPUT (completo) o PATCH (parcial) a /{id}
EliminarDELETE /{id}
Con imagenMultipart: un FormData con la parte config (JSON) y la parte foto (archivo)

El formato de las respuestas

// Éxito
{ "success": true, "message": "Consulta realizada correctamente", "data": { ... } }

// Error
{ "timestamp": "...", "status": 409, "error": "Conflict",
  "message": "...", "path": "/api/compras", "details": { "campo": "ERR01: ..." } }

Lo que hace el fetch parcheado

  • Agrega credentials: "include" para que el navegador mande la cookie de sesión a otro dominio.
  • Desenvuelve la respuesta: los servicios reciben directamente data, no el sobre completo.
  • Reintenta solo las lecturas (GET y HEAD) si Heroku está despertando: hasta 4 veces, esperando 1,5 · 3 · 5 · 8 segundos.
  • Cierra la sesión si una llamada devuelve 401 o 403 fuera de /api/auth/.
  • Detecta la API caída y manda a la pantalla de carga, que decide si va a la página 503.

Paginación segura

Cualquier listado paginado pasa por PaginacionUtils.de(page, size): la página nunca es negativa y el tamaño se fuerza entre 5 y 50 (10 por defecto). Así nadie puede pedir size=99999 y convertir la consulta en un «traeme todo».

Para recordar. Un servicio puede pedir await respuesta.json() y recibir el dato listo gracias al parche; los errores no vienen desenvueltos porque tienen otro formato.
Tema 3

Sesión: cookie y JWT

La sesión vive en una cookie httpOnly que contiene un JWT. La API es quien la emite; el JavaScript del navegador nunca la puede leer, solo el navegador la manda de vuelta.

Dos relojes distintos

RelojDónde viveValor¿Se renueva?
Cookie (Max-Age)Navegador15 minutosSí, en cada petición
JWT (exp)Dentro del token firmado24 horasNo, nunca

La cookie es el envoltorio y el JWT es la carta. Renovar el envoltorio no cambia la fecha de la carta.

Quién emite qué

EmisorCuándoQué hace
AuthControllerAl iniciar sesiónCrea un JWT nuevo y lo pone en la cookie con Max-Age de 900 segundos.
JwtCookieAuthFilterEn cada petición con sesión válidaReenvía el mismo JWT en una cookie con Max-Age de 900 segundos otra vez.

Las cookies y sus atributos

  • authToken para empleados y authTokenPropietario para propietarios: las dos sesiones pueden convivir.
  • HttpOnly, Path=/, y Secure y SameSite según el entorno (en producción None y Secure, porque el frontend y la API están en dominios distintos).
  • El JWT lleva id, rol, tipo, sub (correo) y iss, firmado con HS256.

Línea de tiempo de una sesión

00:00  Login            → cookie vive hasta 00:15
00:10  Petición         → cookie renovada, ahora vive hasta 00:25
00:24  Petición         → renovada, vive hasta 00:39
00:39 → 00:54  sin peticiones   → el navegador BORRA la cookie
00:55  Petición         → no viaja cookie → 401 "No autenticado"
24:00  Aunque haya actividad, el JWT caduca → 401 "Token expirado"

Cómo sabe el frontend quién es

Como el JavaScript no puede leer la cookie, pregunta a la API: GET /api/auth/me/empleado o /me/propietario. Cada variante lee su propia cookie e ignora la otra.

Cierre de sesión

POST /api/auth/logout responde con las dos cookies en Max-Age=0 y los mismos atributos con que se crearon; si no coinciden, el navegador no las borra.

Para recordar. Los 15 minutos significan «15 minutos sin ninguna petición al servidor». Las pantallas se refrescan solas por WebSocket, así que mientras la página esté abierta la cookie se mantiene. El tope absoluto es el JWT de 24 horas.
Tema 4

Recuperar contraseña

La persona escribe su correo, recibe un código de 6 dígitos y con él elige una contraseña nueva. Hay un flujo para empleados (portal web) y otro idéntico para propietarios (app).

PasoEndpoint (público)Qué hace
1. SolicitarPOST /api/auth/recuperar/{empleado|propietario}/solicitarSi la cuenta existe y puede recuperarse, genera el código y lo manda por correo.
2. VerificarPOST …/verificarComprueba el código sin gastarlo, solo para dar respuesta inmediata en la pantalla.
3. RestablecerPOST …/restablecerRevalida el código, lo gasta y guarda la contraseña nueva.

Dónde y cómo se guarda el código

  • En memoria, en un ConcurrentHashMap (CodigoRecuperacionStore). No hay tabla ni entidad.
  • Se guarda su hash (con el PasswordEncoder), no el texto plano.
  • La llave es TIPO:correo en minúsculas. Pedir otro código reemplaza al anterior.
  • El código se genera con SecureRandom: 6 dígitos con ceros a la izquierda.

Los límites

Vigencia

10 minutos. Después se rechaza y se elimina.

Intentos

5 fallidos por código. El sexto obliga a pedir uno nuevo.

Entre envíos

60 segundos. Dentro de ese lapso la API ignora el pedido sin avisar, y la pantalla web muestra «Demasiado rápido».

Respuesta genérica

«Si el correo está registrado, se envió un código», exista o no la cuenta.

Reglas por tipo de cuenta

  • Empleado: solo si su estado es Activo. Se vuelve a comprobar al restablecer.
  • Propietario: basta con que el correo exista.
  • La contraseña nueva debe tener entre 8 y 300 caracteres y se guarda hasheada.

El correo se envía con JavaMailSender (SMTP) con una plantilla HTML de estilos en línea. Una tarea programada limpia cada hora los códigos abandonados.

Para recordar. «Verificar» no consume el código; «restablecer» sí. La seguridad no depende de la sesión (no la hay) sino de recibir el correo, más los límites de tiempo e intentos.
Tema 5

Inicio de sesión con Google

Se usa Google Sign-In con ID token (OpenID Connect). No se piden permisos sobre datos de Google ni se usa un secreto de cliente. Google entrega un JWT firmado que dice quién es la persona y la API lo verifica.

El recorrido

1. Appobtiene el ID token (selector nativo o botón web)
→
2. POST/api/auth/login/propietario/google
→
3. Verificadorfirma, audiencia, vigencia, correo verificado
→
4. Decisiónentra, vincula o rechaza
→
5. CookieJWT propio de PetCore

Qué verifica la API

  • Firma contra las claves públicas de Google.
  • Audiencia igual a nuestro client ID web. Un token emitido para otra app no sirve.
  • Vigencia (exp).
  • email_verified = true. Si Google no verificó el correo, se rechaza.

De ahí salen dos datos confiables: el sub (identificador estable de la persona en Google, que se guarda en PRO_GOOGLE_ID) y el correo.

El árbol de decisión

¿Existe un propietario con ese PRO_GOOGLE_ID?
├── SÍ  → login directo
└── NO  → ¿Existe un propietario con ese correo?
          ├── NO  → 404: "Debes registrarte primero en la clínica"
          └── SÍ  → ¿Tiene contraseña propia?
                    ├── NO → se vincula sola
                    └── SÍ → 409: pide la contraseña actual
                              └── con la contraseña correcta → se vincula

Desvincular Google

SituaciónQué se exige
La cuenta tiene contraseña propiaLa contraseña actual
Solo entra con GoogleVolver a iniciar con la misma cuenta de Google y crear una contraseña nueva en ese mismo paso
Para recordar. Google nunca crea cuentas nuevas: solo activa o enlaza un propietario que la clínica ya registró. Mientras la cuenta esté vinculada, el correo no se puede cambiar, porque es la llave del enlace.
Tema 6

Excepciones y errores

Los controllers y los services no usan try/catch para errores de negocio: lanzan una excepción y un único manejador global (GlobalExceptionHandler) la convierte en una respuesta HTTP con formato estándar.

La jerarquía

RuntimeException
 ├─ GlobalNotFoundException        ← CitasNotFoundException, ProductoNotFoundException…
 ├─ GlobalDuplicateException       ← ComprasDuplicateException…
 ├─ GlobalValidationException      ← ComprasValidationException…
 ├─ GlobalBusinessRuleException    ← VentasBusinessRuleException…
 ├─ GlobalDataIntegrityException
 ├─ GlobalFieldValidationException (lleva un mapa campo → mensaje)
 └─ BadCredentialException / CuentaInactivaException   (módulo auth)

Cada módulo define sus propias excepciones (hay unas 240) pero heredan de estas cinco bases. Por eso el manejador tiene un método por categoría y sirve para los 51 módulos.

Qué HTTP produce cada una

ExcepciónHTTPCuándo
BadCredentialException401Credenciales incorrectas
CuentaInactivaException403Cuenta suspendida o inactiva
GlobalNotFoundException404No existe el registro
GlobalDuplicateException409Duplicado (factura, comprobante, correo)
GlobalValidationException400Regla de validación del service
GlobalBusinessRuleException409Regla de negocio (descuento mayor al subtotal, capacidad)
GlobalDataIntegrityException409Integridad a nivel de dominio
GlobalFieldValidationException400 + detailsValidación manual (multipart, líneas)
MethodArgumentNotValidException400 + detailsFalla de @Valid en un DTO
Violación de restricción de Oracle409UNIQUE, llave foránea, CHECK
Ruta inexistente404Endpoint mal escrito
Exception (cualquier otra)500Error interno no controlado

Spring Security responde aparte, con el mismo formato: 401 «No autenticado» o «Token expirado», y 403 «No tienes permiso».

Cómo lo interpreta el frontend

extraerMensajeError sigue este orden de prioridad:

  1. Si el cuerpo trae details con un solo campo, usa ese mensaje. Con varios, los une uno por línea.
  2. Si no, usa message.
  3. Si no hay nada coherente, usa el mensaje por defecto del servicio.
  4. Antepone el código HTTP: [409 Conflict] ….

Después lanzarErrorApi lanza un Error con dos datos extra: error.status (para ramificar, por ejemplo 409 = duplicado) y error.detalles (el mapa por campo).

  • Si el cuerpo no es JSON y el estado es 502, 503 o 504, avisa que el servidor tardó y que la acción pudo haberse aplicado, para evitar duplicados.
  • esCaidaDelServidor(error) distingue un fallo de red o de gateway de un error de negocio.
  • Algunos módulos tienen un traductor propio: interpretarErrorEmpleado convierte nombres de restricciones de Oracle (UQ_EMP_DUI) en frases claras.
  • La app híbrida arma el Error a mano en cada servicio, con status y a veces details.
Para recordar. El éxito viene en {success, message, data} y el error en ErrorResponse. El fetch parcheado solo desenvuelve los éxitos.
Tema 7

WebSocket

Es un WebSocket simple, sin STOMP ni broker, en un único endpoint /ws. Cuando algo cambia, la API manda un aviso a todas las sesiones conectadas y cada pantalla decide si le interesa.

Qué ocurre cuando cambia algo

→
Espera el commitsolo avisa si la transacción quedó firme
→
Serializa 1 vezun JSON para todos
→
Pool de envíoun hilo por sesión
→
Clientevuelve a pedir por REST

Eventos

EventoCuándo
CITA_ACTUALIZADACrear, editar, cancelar, iniciar o terminar consulta y autocancelaciones
NOTIFICACION_NUEVANueva notificación (lleva empIds o proId para filtrar en el cliente)
PRODUCTO_ACTUALIZADOCambio de stock o datos del producto
SOLICITUD_BODEGA_ACTUALIZADASolicitud de stock
ASISTENCIA_ACTUALIZADA / ASISTENCIA_LOTE_TERMINADOAsistencias

CONFIG_SISTEMA_ACTUALIZADACambio de configuración (IVA, logo)
WS_ESTADO, WS_RECONECTADOSolo en el navegador: estado de la conexión

Mecanismos de robustez

  • Heartbeat doble. El servidor manda un ping cada 25 s (el router de Heroku corta a los 55 s sin tráfico). El cliente manda "ping" cada 25 s y espera "pong" en 10 s; si no llega, reconecta.
  • Reconexión con espera creciente: 1, 2, 4… hasta 30 s, con algo de azar para que varias pestañas no golpeen a la vez.
  • WS_RECONECTADO: lo que se difundió mientras estuvo caído se perdió, así que las pantallas revalidan contra la API.
  • Cliente lento: ConcurrentWebSocketSessionDecorator corta la sesión si tarda más de 5 s o acumula más de 256 KB.
  • Cola acotada: pool de 2 a 4 hilos y 2000 envíos pendientes.
Para recordar. El WebSocket casi nunca lleva los datos: dice «cambió una cita» y la pantalla refresca con un GET.
Tema 8

Notificaciones push

Hay dos canales distintos que se disparan a la vez desde NotificacionesService: Web Push para el navegador del portal y Firebase Cloud Messaging (FCM) para la app Android.

Web Push en el portal

PetCore no contrata un proveedor propio. Web Push es un estándar abierto y el mensaje lo entrega el servicio push del fabricante del navegador:

NavegadorServicio que entrega el mensaje
Chrome, Edge, Brave, OperaGoogle FCM (fcm.googleapis.com)
FirefoxMozilla autopush
SafariApple Push

Suscripción (una vez por navegador)

  1. El frontend registra el service worker sw.js y pide permiso.
  2. Pide la llave pública VAPID a la API (GET /api/push/vapid-public-key).
  3. pushManager.subscribe(...): el navegador contacta a su servicio push y devuelve endpoint, p256dh y auth.
  4. POST /api/push/suscripciones (con sesión) los guarda ligados al empleado o propietario del JWT.

Envío y recepción

  1. La API arma un JSON {titulo, mensaje, enlace}.
  2. La librería web-push lo cifra con las llaves de la suscripción y lo firma con la llave privada VAPID.
  3. Lo manda por HTTPS al endpoint; el servicio push lo reenvía al navegador.
  4. El service worker recibe el evento push, muestra la notificación y, al hacer clic, abre o enfoca la página del enlace.

Push nativo en Android (FCM)

Al abrir la appcrea el canal petcore_alertas y pide permiso
→
Tras iniciar sesiónobtiene el token FCM y lo registra
→
APIsendEach con firebase-admin
→
Androiddibuja la notificación aunque la app esté cerrada
  • El mensaje lleva notification (para que el sistema la dibuje solo) y data (para que el JS sepa a dónde navegar).
  • Prioridad HIGH y canal de importancia alta: sin eso, el modo Doze de Android la retrasa varios minutos y entra callada.
  • Al tocarla, pushNotificationActionPerformed traduce el código de enlace (por ejemplo CITAS) con un mapa de destinos.
  • Si FCM responde UNREGISTERED (o el servicio push responde 404 o 410) la API borra esa fila.
Para recordar. Una suscripción pertenece al navegador, no a la persona. La unicidad es el par (endpoint, dueño): dos empleados en la misma PC tienen filas distintas con el mismo endpoint.
Tema 9

Asincronía y pools de hilos

«Asíncrono» aquí significa mover trabajo secundario (notificaciones, push, lotes) fuera del hilo que atiende la petición, para responder antes y liberar hilos de Tomcat.

Por qué no basta con la anotación

  • @EnableAsync activa el mecanismo, que funciona con un proxy: Spring intercepta la llamada y la manda a un pool.
  • Si un método @Async se llama desde la misma clase, no pasa por el proxy y corre síncrono. Por eso existe DespachadorAsincrono, un bean aparte cuyo único método recibe un Runnable.
  • El hilo asíncrono no comparte la sesión de Hibernate: los datos con relaciones lazy se resuelven antes (por ejemplo, el id del propietario se convierte en un Long antes de lanzar la tarea).
  • Un fallo asíncrono no revierte lo ya guardado: cada notificación tiene su propio try/catch.

Trabajos largos con seguimiento

Para el lote de asistencias, la API devuelve de inmediato un jobId con estado PROCESANDO, procesa en segundo plano y al terminar avisa por WebSocket (ASISTENCIA_LOTE_TERMINADO). El estado vive en un mapa en memoria y se limpia a los 30 minutos.

Para recordar. Lo asíncrono no reduce el trabajo total: reduce lo que el usuario espera. Todos los pools compiten por solo 8 conexiones de base de datos, que es el techo real.
Tema 10

Rendimiento y el problema N+1

El Eco dyno es modesto (unos 512 MB de RAM, un proceso, y se duerme tras 30 minutos sin tráfico). La API responde bien porque cada petición toca poco.

Qué es el N+1

Pedir una lista de N filas (1 consulta) y luego, al convertir cada una a DTO, tocar una relación lazy que dispara otra consulta por fila (N más). Con 100 citas son 101 consultas.

Las soluciones que se aplicaron

1. JOIN FETCH y EntityGraph

Una sola consulta con JOIN trae la entidad y sus relaciones. Hay 67 JOIN FETCH y muchos @EntityGraph en los repositorios.

2. Batch fetch de 50

default_batch_fetch_size=50: lo que sigue lazy se carga de 50 en 50 con WHERE id IN (...). Mil citas pasan de 1.000 consultas a unas 20.

3. Conteos agrupados

En vez de cargar una colección para hacer .size(), una consulta GROUP BY con ids en bloques de 500 (el IN de Oracle admite 1.000).

4. Menos viajes HTTP

Endpoints de resumen y de búsqueda paginada: los KPIs salen de COUNT y SUM en la base, sin entidades.

El caso documentado: GET /api/ventas/por_fecha pasaba de 28 segundos con unas 500 ventas porque cargaba las líneas de cada venta solo para contarlas; con la consulta agrupada dejó de ser un problema.

Por qué cabe en poca memoria

  • Todas las relaciones son LAZY (170) y ninguna EAGER.
  • Paginación forzada (5 a 50 filas) y fetch_size=100 para menos viajes a Oracle.
  • Pools acotados: Tomcat 30, Hikari 8, async ~8.
  • Sin sesiones en memoria: el JWT va en la cookie.
  • WebSocket en lugar de polling; el trabajo secundario va fuera del hilo de la petición.
  • Precalentamiento de Firebase al arrancar, para que el primer push no pague el handshake.

El arranque en frío

Tras dormirse, la primera petición despierta la JVM y abre conexiones a Oracle, y puede responder 502, 503 o 504. El frontend reintenta las lecturas con espera creciente (suma de unos 17,5 s, por debajo de los 30 s que Heroku tolera).

Para recordar. Las relaciones LAZY son lo correcto, pero exigen decidir cómo se cargan en cada consulta: unir, agrupar o traer por lotes.
Tema 11

La app híbrida y el porteo a iOS

No hay una app iOS separada: es el mismo código web empaquetado con Capacitor dentro de un WKWebView. Lo difícil no fue la interfaz sino que iOS trata las cookies, los orígenes y las peticiones de otra manera que Android.

Problemas y soluciones

ProblemaQué se hizo
La cookie de sesión no viajaba al dominio de la API (bloqueo de cookies de terceros)Activar CapacitorHttp y CapacitorCookies: las peticiones salen por la red nativa y las cookies viven en un almacén nativo.
El origen de la app en iOS es capacitor://localhostiosScheme: "https" en la configuración, y esos orígenes agregados al CORS y al WebSocket de la API.
El XHR síncrono de verificación de sesión se saltaba el puente nativo: iOS veía «sin sesión» y expulsaba al usuario recién logueadoVersiones asíncronas con fetch (verificarSesionAsync); requerirSesion() y obtenerSesion() pasaron a devolver Promesas.
«Cerrar sesión» no hacía nada: la cookie no se borrabaUna marca local pc_cierre_sesion y limpieza explícita de las cookies nativas.
Google bloquea OAuth dentro de un WebViewPlugin nativo de inicio de sesión, con GIDClientID y el esquema de URL invertido en Info.plist.
El tema se decide antes del primer render y su consulta síncrona falla en iOSSe guarda el último id de propietario como respaldo para leer las preferencias.

Para recordar. El puente nativo de Capacitor es asíncrono: cualquier petición síncrona queda fuera de él. Por eso la verificación de sesión se reescribió con fetch.
Tema 12

Concurrencia y consistencia de datos

Cuando dos personas hacen algo a la vez, el resultado correcto no puede depender de quién llegó primero por casualidad. Las transacciones y los bloqueos hacen que dos operaciones simultáneas no se pisen.

Vocabulario

TérminoSignificadoEjemplo en PetCore
ACIDAtomicidad, consistencia, aislamiento y durabilidadCompra y líneas en una sola transacción
Condición de carreraEl resultado depende del orden de ejecuciónDos cajeros venden la última unidad
Check-then-actComprobar y luego actuar, sin bloquear entre mediovalidarStockDisponible

Caso: la última unidad

  1. La API lee el stock y compara con la cantidad pedida (validarStockDisponible). Es una comprobación sin bloqueo.
  2. Dos ventas simultáneas pueden leer stock = 1 y pasar las dos.
  3. El trigger TRG_DETALLE_VENTA_STOCK descuenta con una resta relativa: SET stock = stock - :cantidad.
  4. Oracle bloquea la fila: la segunda transacción espera a que la primera confirme.
  5. Al entrar, el stock ya es 0 y la restricción CHECK (PROD_STOCK_DISPONIBLE >= 0) la rechaza y la revierte.
Para recordar. La validación de la aplicación es para la experiencia; la restricción de la base de datos es para la verdad.
Tema 13

Glosario rápido

JWT
Token firmado que contiene quién eres (id, rol, tipo) y cuándo caduca.
httpOnly
Cookie que el JavaScript de la página no puede leer.
SameSite
Regla que controla si la cookie viaja en peticiones desde otro sitio.
CORS
Lista de orígenes que la API permite y reglas para llamadas entre dominios.
Preflight
Petición OPTIONS previa que el navegador hace antes de una llamada entre dominios.
DTO
Objeto que viaja por la red; separa lo que se expone de la entidad de base de datos.
Entity
Clase que representa una fila de una tabla.
LAZY / EAGER
Cargar una relación cuando se usa / cargarla siempre junto con la entidad.
N+1
1 consulta de lista más N consultas, una por fila, para leer relaciones.
JOIN FETCH
Traer una entidad y sus relaciones en una sola consulta.
Hikari
Pool de conexiones a la base de datos.
Proxy (Spring)
Objeto que intercepta llamadas para añadir transacciones o asincronía.
@Async
Ejecuta un método en otro hilo, a través del proxy.
VAPID
Par de llaves que identifica al servidor ante el servicio push del navegador.
FCM
Firebase Cloud Messaging: servicio de Google para push a dispositivos.
Doze
Modo de ahorro de Android que retrasa mensajes de prioridad normal.
Heartbeat
Mensaje periódico que mantiene viva una conexión y detecta si está muerta.
Capacitor
Empaqueta una web como app nativa y da acceso a funciones del dispositivo.
WKWebView
Componente de iOS que muestra páginas web dentro de una app.
ID token
JWT firmado por Google que identifica a la persona que inició sesión.
Idempotente
Operación que da el mismo resultado si se repite.
Trigger
Código de la base de datos que se ejecuta ante un insert, update o delete.
